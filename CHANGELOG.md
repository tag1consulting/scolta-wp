All notable changes to scolta-wp will be documented in this file.

This project uses [Semantic Versioning](https://semver.org/). Major versions are synchronized across all Scolta packages; minor and patch versions are released independently per package.

## [1.2.0] - 2026-08-07

### Added
- **`UPGRADE.md`, with the 1.2 upgrade notes, and a `= 1.2.0 =` section in `readme.txt`.** This plugin's own PHP API is unchanged in 1.2.0 and the file says so rather than implying a break. It records the two breaks inherited through the vendored library, the `AmazeeCredentials` constructor signature and the `aiProvider` default, reachable only by a site with custom PHP calling into the `Tag1\Scolta\` namespace directly; the no-default-provider change on activation and how to restore AI features; and that facet counts will read lower than in 1.1.x because that is the fix rather than a regression, so anything asserting exact counts against an expanded query needs re-baselining. `UPGRADE.md` is developer facing and stays in the repository: `build-dist.sh` stages an explicit allowlist of PHP, assets and `vendor/`, so it is not in the shipped zip, and the site owner facing summary is the `readme.txt` changelog section that WordPress.org renders.

### Changed
- **`tag1/scolta-php` is required as `^1.2.0` from Packagist, and the plugin stops consuming an unreleased core (`composer.json`, `composer.lock`).** The requirement was `dev-main`, backed by `"minimum-stability": "dev"` and a VCS repository entry pointing at the scolta-php GitHub repo. That was the right answer during the coordinated cycle, for the reason the entry below records: this plugin vendors `vendor/` into the archive it ships, so the lock is the only thing deciding which core the artifact actually carries, and tracking the branch kept the artifact and the code in step. scolta-php 1.2.0 is now tagged and on Packagist, so the cycle closes: the constraint becomes `^1.2.0`, `minimum-stability` returns to `stable`, and the VCS repository entry is removed because Packagist supplies the package. `composer.lock` names the 1.2.0 release resolved from Packagist. A published plugin no longer depends on a development constraint, and the shipped zip vendors a released core rather than whatever `main` pointed at when someone last ran composer. `extra.branch-alias.dev-main` moves from `1.1.x-dev` to `1.2.x-dev` in the same commit: a consumer resolving `dev-main` is aliased onto whatever line the alias names, so leaving it on 1.1 would have left `dev-main` unable to satisfy the `^1.2.0` required here.

### Fixed
- **Re-vendored the browser bundle (`assets/js/scolta.js`) from scolta-php 1.2.0: facet counts stop reading high, and a facet value no visible result carries is no longer offered.** Two changes in the released bundle, both in the count path. The expansion delta is now collapsed exactly as the result list collapses it, through `mergeResults()` and then `deduplicateByTitle()`, **before** any value is counted, so a document the list folds away is no longer counted behind a row the user cannot reach; on a corpus with formulaic titles the panel read one high per collapsed pair. And `suppressUnreachableValues()` zeroes any value that no document in the ranked list carries, so a count is again a promise that clicking it produces results rather than a click through to "No results found". It stands down when the user has a facet selection active, where presence in the list is not a sound reachability test, and when a deployment's fragments carry no `filters` at all. Copied from `vendor/tag1/scolta-php/assets/` with `composer copy-assets` against the locked 1.2.0 release; `assets/css/scolta.css` and both WASM assets were already byte-identical to 1.2.0 and are unchanged.

### Fixed
- **The shipped plugin no longer fatals on activation: the zip vendors the core it is written against (`composer.json`, `composer.lock`, `.github/workflows/ci.yml`).** This plugin bundles `vendor/` into the archive it ships, so `composer.lock` alone decides which scolta-php a site actually runs. The lock pinned the 1.1.0 release while this branch's code referenced 1.2.0-dev API, and `Scolta_Amazee_Config_Storage implements ProvenanceAwareConfigStorageInterface` resolves at **class load**, not at call time — so `wp plugin activate scolta` died with `Uncaught Error: Interface ... not found` before anything ran. WordPress.org's Plugin Check, which builds the real archive and activates it, caught exactly that. The constraint now tracks the core's development branch (`dev-main`) for the duration of this cycle, which is how the plugin consumes unreleased core work; it returns to a release constraint when the cycle closes. The `path` repository is replaced by the project's VCS repository so the committed lock resolves identically on every machine and in CI, rather than recording whichever filesystem last ran Composer. **No release was tagged to achieve this** — the 1.2.0-dev line is consumed directly, which is what a `-dev` version is for.
- **Two CI guards encoded the assumption that the only consumable core is a tagged release.** `lock-guard` required the locked scolta-php version to match `\d+\.\d+\.\d+`, and `version-alignment` skipped its major-version comparison only for the literal `@dev` constraint. Both made the `-dev` workflow impossible for the one adapter that vendors its dependency. The lock guard now accepts a tagged release **or** a tracked dev branch, and keeps its load-bearing rule unchanged and absolute: `dist.type=path` is still rejected outright, because a path-resolved lock records the filesystem of whoever ran Composer and installs nowhere else. `version-alignment` now treats any `dev-*` constraint as development mode, which is what it already did for `@dev`.

### Changed
- **No AI provider is selected on activation, and connecting Amazee.ai is two explicit actions (`scolta.php`, `admin/class-scolta-admin.php`, `admin/class-scolta-amazee-admin-page.php`, `assets/js/amazee-admin.js`, `includes/class-scolta-ai-service.php`, `includes/class-scolta-amazee-config-storage.php`, `cli/class-scolta-cli.php`).** Activation seeded `ai_provider => 'anthropic'`, the provider select fell back to inferring a selection from the API key source when nothing was saved, `resolve_api_key()` coalesced an empty value back to `'anthropic'`, and the settings sanitiser corrected an unrecognised value to it as well — so a site nobody had configured presented itself as an Anthropic site on every surface it has. Activation now seeds `''`, the select opens on a *- Select a provider -* option, nothing coalesces, and `''` is an accepted value rather than one to be corrected: an unrecognised provider fails closed to "none selected" instead of quietly enabling a vendor. **Going-forward only — no existing setting is touched**, which `test_activation_merges_with_existing_settings` already pins.
- **Version coherence is checked on every pull request (`scripts/check-coherence.mjs`, `.github/workflows/ci.yml`).** The existing `version-sync` job compares MAJOR version numbers, which cannot see the break that actually happened: [scolta-php#275](https://github.com/tag1consulting/scolta-php/pull/275) moved that package's `version` to `1.2.0-dev` and left `extra.branch-alias.dev-main` on `1.1.x-dev`, and 1 against 1 passed. The retired `check-version-sync.php` had the same blind spot and was wired into no workflow anywhere. The new `coherence` job compares the development *line* and reads every place this package states its own version, so a package that contradicts itself fails on its own checkout with no sibling repositories present. It is generated from TypeScript in the scolta-fleet repository and vendored here as a dependency free bundle, because that repository is private and this one is public; GitHub runners ship node, so the job needs no setup step and no install. Regenerate with `npm run vendor:coherence` in scolta-fleet.
- **The Amazee demo takes no email, and the credential path is a separate labelled action.** `ajax_start_trial()` rejected any request whose `email` was not a valid address, and the start step put one required field above both buttons — so the cheapest possible way to evaluate Scolta's AI, one click, cost an administrator their address first, and the two paths differed only in which button was pressed. The start step is now two sections. **Try the demo** posts nothing at all and calls `provision()` with no argument; the browser no longer reads the field for it. **Enter your Amazee credentials** keeps the email → verification code → region flow, with the field inside that section. There is deliberately no paste-your-API-key input: amazee.ai issues and manages the credentials exactly as its own `ai_provider_amazeeio` module does. A refused demo — it is one-time per site — now says so and points at the account path.
- **`scolta_auto_provision_amazee()` establishes the demo itself instead of delegating to a helper that no longer does (`scolta.php`).** It called `AutoProvisioner::ensureAiAvailable()`, which minted a demo whenever it found an empty credential store. That contract is removed upstream — anything else reaching that helper would have enrolled a site that never opted in — so this click would have silently done nothing. It now calls `AmazeeTrialProvisioner::provision()` directly with no email, states the explicit-key and already-stored guards it used to inherit, and still runs the self-heal (model re-resolution against the key already on disk) for a half-provisioned store. Its one caller, the administrator's action, is unchanged.
- **Which action established the connection is recorded, so the status line states a fact (`includes/class-scolta-amazee-config-storage.php`, `admin/class-scolta-admin.php`, `cli/class-scolta-cli.php`).** [scolta-php#273](https://github.com/tag1consulting/scolta-php/pull/273) collapsed the two Amazee source cases because nothing recorded which produced a token, and on WordPress the surviving guess was the wrong one: **every deliberately connected account was announced as an auto-provisioned free trial**. Recording the fact is the fix rather than guessing at it or giving it up. `Scolta_Amazee_Config_Storage` now implements scolta-php's `ProvenanceAwareConfigStorageInterface`, keeping the connection source in its own option beside the credentials and deleting it in `clear()`. The settings notice and `wp scolta status` report `AmazeeDemo` / `AmazeeAccount` — "using the free demo", "with your account" — while a connection made before this release still reports the origin-free `Amazee` and claims nothing. Free-trial wording is gone from the opt-in notice, the result notice, the budget-exceeded notice and `readme.txt`. **Requires scolta-php ≥ 1.2.0 (unreleased)**; the committed `composer.lock` stays pinned at the stable release and is bumped once that is tagged.

### Changed
- **Amazee.ai is reported as one API key source, and a deliberately connected account is no longer called a free trial (`includes/class-scolta-ai-service.php`, `admin/class-scolta-admin.php`, `cli/class-scolta-cli.php`, [scolta-php#273](https://github.com/tag1consulting/scolta-php/pull/273)).** 1.1.0 split the source into `amazee:operator` and `amazee:auto` to separate a licensed connection from an auto-provisioned trial, but nothing records which one produced a token: the trial provisioner and the account upgrader persist the same three fields. Each adapter therefore substituted a local fact, and this one had none to substitute — `operatorChosen` was `$provider === 'amazee'`, and **nothing in this plugin ever writes `'amazee'` to `ai_provider`**, so it was permanently false and `amazee:operator` was unreachable. Every WordPress site with stored credentials, however deliberately it had connected them, was told on its settings screen that it was "Connected to Amazee.ai (auto-provisioned free trial)" and got the same wording from `wp scolta status`. Upstream has collapsed the pair back to a single `ApiKeySource::Amazee`; `get_api_key_source()` now returns `'amazee'`, and both surfaces say "Amazee.ai (managed gateway)" — the wording that describes what the connection is rather than guessing where it came from. `env`, `constant`, `database` and `none` are unchanged, as is `is_amazee_active()`, which reads the same single resolution it already did.

### Fixed
- **Re-vendored the browser bundle (`assets/js/scolta.js`) from scolta-php: the AI summary's "Show more" control now follows the viewport width, and a summarize failure can no longer strand the loading skeleton**
  ([tag1consulting/scolta-php#269](https://github.com/tag1consulting/scolta-php/pull/269)).
  Two follow-ups to the layout reservation. **First**, whether to clamp the summary and offer the control is a measurement (`scrollHeight` against `clientHeight`), and it ran only on resolve and on a toggle click, so the decision froze at the width the summary landed in. Rotate a phone to portrait, or shrink a responsive column, and a summary that fitted reflows past the reserved height: the text is still clipped, but with no clamped class there is no fade and the control stays hidden, so **a sighted reader saw text cut off at the box edge with no on-screen way to open it** (the full text stays in the DOM, so find-in-page and assistive tech were never affected). Widening left a pointless control behind. This is the defect a responsive WordPress theme was most likely to hit, since the summary sits in a column whose width tracks the breakpoint. A feature-detected `ResizeObserver` on the text region now recomputes it, with exactly one live at a time, disconnected when the slot is released and when the user expands the summary, re-established on collapse, and never installed when the AI summary is off. The recompute toggles a mask class and the control's `hidden` flag inside the fixed-height panel, and the reserved height derives from a line count rather than the width, so **the box measures the same at every width** (297.03px at both 1280px and 420px) and the reveal moves nothing. **Second**, the search flow's un-awaited `summarizeResults(...)` call had nothing chained onto it; the work before its fetch is outside its own error handling, and because the function is `async` a throw there became a rejected promise the expansion chain's `.catch` never saw. With the slot reserved from the result paint, that left a skeleton shimmering permanently. The call now carries its own `.catch`, guarded on the search version so an abandoned cycle cannot collapse a newer search's slot. No new option, no settings field, no index rebuild. Copied byte-identically from the canonical `scolta-php` assets with `composer copy-assets`, verified with `cmp`.

### Fixed
- **Re-vendored the browser bundle (`assets/js/scolta.js`, `assets/css/scolta.css`) from scolta-php: the AI summary no longer shoves the result list down when it arrives**
  ([tag1consulting/scolta-php#268](https://github.com/tag1consulting/scolta-php/pull/268)).
  The summarize call is deferred until query expansion settles so the model ranks what the user sees, which means the result list is already painted when the summary lands above it. Inserting it there pushed the list down **twice**: once when the loading skeleton appeared (+177px, CLS 0.120) and again when the resolved summary replaced it (+342px, 0.317), for 0.437 against a "good" threshold of 0.1. The first push is invisible to any measurement that stubs expansion faster than 500ms, because the browser credits a shift within 500ms of a click to the user and excludes it, and a real expansion is an LLM round trip that is not that fast. **The slot now takes a fixed height in the same frame the results paint in and holds it** through loading, resolution and error alike: the panel is a flex column with `overflow: hidden` and the text region is its only flexible child, so the text absorbs whatever the chrome around it does or does not occupy and the panel is the same height in every state. A summary taller than the box is clipped behind a **Show more** button (`aria-expanded`, `aria-controls`, keyboard operable) with the full text always in the DOM, clipped rather than truncated, so find-in-page and assistive tech reach all of it; expanding is user-initiated, which the metric excludes. Measured after: **0.000 for a normal summary, a long clamped summary and a summarize failure alike**, and 0.000 added by a Show more click. An empty summary still collapses by design (0.215, against 0.240 before). The collapsed height is tuned with the CSS custom property `--scolta-summary-collapsed-lines` (default `6`), so **a WordPress theme retunes it in one line of CSS** — there is no new option, no settings field, no `toBrowserConfig()` parity change and no index rebuild. With the AI summary disabled the slot reserves nothing and the layout is byte-identical to before. Copied byte-identically from the canonical `scolta-php` assets with `composer copy-assets`, verified with `cmp`.

### Added
- **Re-vendored the browser bundle (`assets/js/scolta.js`) from scolta-php: search-as-you-type suggestions now carry their fragment metadata, and a theme can render the suggestion row itself ([scolta-php#267](https://github.com/tag1consulting/scolta-php/pull/267)).** SAYT shipped in 1.1.0 with two lifecycle events and no per-suggestion renderer, on the reasoning that a suggestion row is a title and an excerpt and CSS is enough for it. A theme that wants a thumbnail on each row could get one from neither half: the suggestion object handed to `scolta:suggestions-rendered` carried `type`, `title`, `url`, `safeUrl` and `excerpt`, and the fragment's `meta` map — where an indexed image, post id or post type lives — was dropped before the event fired. Two additions close that. **Every suggestion now carries `meta`**, the fragment's whole metadata map on a title suggestion and `{}` on a recent search, so the shape is uniform and a listener never has to feature-test the field; the values are raw index content, deliberately unescaped at the source, because escaping there would corrupt a value wanted for a request URL or a comparison, and the built-in row renders no `meta` value, so a poisoned key has no path to markup on its own. **`Scolta.setSuggestionRenderer(fn)` and the per-instance `instance.setSuggestionRenderer(fn)`** mirror `setResultRenderer` exactly, are called as `fn(suggestion, ctx)` once per row with `ctx` carrying `index`, the raw `query` and the pre-escaped `titleHtml`, `excerptHtml` and `safeUrl`, and fall back to the built-in row for one suggestion on a non-string return or a throw. A renderer owns the inside of the row and not the row: the option element keeps `role="option"`, its stable id, `aria-selected`, `data-scolta-sayt-index` and the sanitized `href`, so arrow-key navigation and screen-reader announcement cannot be broken by an omission in theme code. **Both are opt-in and additive** — register nothing, read no new key, and the dropdown behaves byte-identically. **No index rebuild is needed and nothing on the WordPress side changed**: like `setResultRenderer` these are browser-side registration functions, so there is no new `ScoltaConfig` property, no settings field, no option to sanitize and nothing for `toBrowserConfig()` to emit. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js` with `composer copy-assets`, verified with `cmp`; the CSS and WASM assets are untouched.
- **`.github/upstream-preview` names the scolta-php branch this re-vendor comes from,** so the informational preview job runs this plugin's suite against the unmerged upstream instead of against `dev-main`, which cannot contain the new bundle yet. Remove the file (or set it to `main`) once scolta-php has merged.

## [1.1.0] - 2026-08-01

### Added
- **Search as you type, with a first-class settings section (`admin/class-scolta-admin.php`, `includes/class-scolta-shortcode.php`, `scolta.php`, re-vendored `assets/js/scolta.js` + `assets/css/scolta.css`; [tag1consulting/scolta-php#247](https://github.com/tag1consulting/scolta-php/pull/247)).** Typing in the search box now populates a suggestions dropdown under it, merging the visitor's own recent searches ahead of content suggestions. The full pipeline — AI query expansion, the AI summary, follow-ups — still runs only on Enter, on the search button, or on picking a suggestion; the suggest path never writes the result list, the facet panel or the history, and never triggers a summary. **On by default, and no index rebuild is required**: suggestions read the index the site already has. Set `sayt_enabled` to `false` and the widget is the pre-1.1.0 one exactly — no dropdown node, no combobox ARIA roles on the input, no browser storage access, no suggest searches. Ten settings, all first-class in a new **Search as you type** section on the settings screen (three checkboxes, six bounded number inputs, one select), each with an `add_settings_field` registration, a render callback and a sanitizer line: `sayt_enabled` (on), `sayt_min_chars` (`2`, counted in graphemes so an emoji is one character; CJK sites usually want `1`), `sayt_debounce_ms` (`150`), `sayt_max_suggestions` (`6`), `sayt_recent_searches` (on, one `localStorage` key, nothing read or written when off), `sayt_max_recent` (`3`), `sayt_expand` (on), `sayt_expand_per_minute` (`6`), `sayt_expansion_delay_ms` (`500`) and `sayt_suggestion_action` (`navigate`, or `search` to run the full search instead; a recent search always searches). The enrichment cap is not arbitrary and its description says so on the screen: SAYT expansions spend the same per-visitor AI budget that expansion, summarization and follow-ups spend for committed searches, so an uncapped suggest path would let a visitor's typing exhaust the allowance and starve the search they actually ran; over the cap the dropdown degrades to keyword-only suggestions until the window rolls. All ten defaults are byte-equal to the fallbacks the browser bundle uses when a key is absent, so a site that upgrades and changes nothing gets the documented behaviour. The sanitizer lines are not optional: `sanitize_settings()` is a strict rebuild-from-scratch allowlist registered as the option's `sanitize_callback`, so a key it does not write is dropped on every save. All ten are also bridged top-level through `wp_localize_script()` as `saytEnabled`, `saytMinChars`, `saytDebounceMs`, `saytMaxSuggestions`, `saytRecentSearches`, `saytMaxRecent`, `saytExpand`, `saytExpandPerMinute`, `saytExpansionDelayMs` and `saytSuggestionAction` — the same bridging `hideEmptyFacets` uses — with the suggestion action passed through `ScoltaConfig::normalizedSaytSuggestionAction()` so an unrecognized stored value reaches the browser as `navigate` rather than as itself. They are top-level keys, not scoring keys: `toJsScoringConfig()` stays at exactly 40. **No new network calls and no telemetry**: suggestions search the local index in the browser, recent searches never leave the visitor's device, and the optional AI enrichment reuses the plugin's existing `scolta/v1/expand-query` endpoint and the AI provider the site already configured, so the wordpress.org consent rules are not triggered by anything in this change. Covered by `tests/AdminSaytFieldsTest.php` (section registration, all ten fields registered in it, every registered renderer emitting a bound control and a description, defaults, bounds, clamping high and low, zero preserved where zero is meaningful, the unknown-action fallback in both the renderer and the sanitizer, and a full submit-save-reload round trip) and by four new cases in `tests/ShortcodeTest.php` asserting the ten emitted keys by value, a non-default round trip for all ten, and the action normalization. `tests/BrowserConfigParityTest.php` needed no change and is the reason the emission tests matter: it fails on any `instanceConfig.<key>` the bundle reads and the localize array omits, which is exactly how `filterFieldDescriptions` shipped dead client-side. Browser assets are copied byte-identically from the canonical `scolta-php` `main`; the CSS is in this re-vendor too, since SAYT adds the dropdown's styles and its theming custom properties.
- **Re-vendored the browser bundle (`assets/js/scolta.js` + `.sha256`): a platform render seam, so a WordPress site can supply its own result markup instead of Scolta's card ([tag1consulting/scolta-php#246](https://github.com/tag1consulting/scolta-php/pull/246)).** Three additions in the canonical bundle, none of which change anything for a site that does not use them. **(1)** Four render lifecycle events on the elements Scolta writes, bubbling and non-cancellable: `scolta:before-results-render` (`{container, reason}`) and `scolta:results-rendered` (`{container, results, rendered, reused, appended, query}`) around every write to `#scolta-results`, and `scolta:before-filters-render` / `scolta:filters-rendered` around the `#scolta-filters` write. `reason` distinguishes the "Searching..." placeholder, the primary paint, the post-expansion repaint and the "show more" append, so a theme or plugin can detach a behaviour before its nodes are destroyed and re-attach after. **(2)** `Scolta.setResultRenderer(fn)` (plus a per-instance form), which replaces the built-in card with `fn(data, ctx) -> string | null`; returning `null` falls back to the built-in card for that result alone. `ctx` hands over the already-escaped, `<mark>`-wrapped excerpt, title, and a scheme-neutralized URL. It is a registration function rather than a config key, so nothing travels through `wp_localize_script()` and this re-vendor adds no setting and no key to `sanitize_settings()`; `tests/BrowserConfigParityTest.php` passes unmodified for exactly that reason. **(3)** `init()` no longer runs `root.innerHTML` over the mount point, so markup already inside the shortcode's container survives initialisation. Also in this bundle: the repaint after AI query expansion now reconciles the result list by identity instead of replacing it, so an expansion that reorders nothing moves no DOM node. Copied byte-identically from the canonical `scolta-php/assets/js/scolta.js`, verified with `cmp`. Note that CI does not verify this: `composer update` fires `post-update-cmd` → `copy-assets`, which overwrites `assets/js/scolta.js` from the vendored scolta-php before the "Verify duplicated assets match canonical" step runs, so that step compares a file Composer just wrote against the manifest of the source it wrote it from and can never fail on a stale committed copy. The plugin suite in CI therefore exercises scolta-php `main`'s bundle, not this one; the bundle in this PR was exercised locally through the `../scolta-php` path repo (773 tests). `.sha256` is not in `copy-assets` at all, which is exactly why it could drift (see Fixed).
- **The six specificity and co-occurrence ranking settings are now configurable from WordPress (`admin/class-scolta-admin.php`, `scolta.php`, `README.md`, `readme.txt`).** `specificity_weighting` (bool, default on), `specificity_floor` (`0.15`), `specificity_strong_match` (`0.55`), `specificity_cooccurrence` (`0.9`), `specificity_agreement_gate` (`0.45`) and `specificity_agreement_decay` (`1.0`) each get an `add_settings_field` registration in the Scoring section, a render callback, a sanitizer line with clamping, and an activation default. `scolta.js` has read all six for some time and scolta-php now carries all six as typed properties, but WordPress exposed none of them, so every site was pinned to the hardcoded JS fallbacks. Defaults are byte-equal to those fallbacks, so an existing site's ranking does not move; `specificity_cooccurrence` at `0` scores each result purely by its single best-matching sub-query. The floor, strong-match and agreement gate clamp to `0.0`-`1.0`; the co-occurrence bonus and agreement decay are multipliers and clamp to `0.0`-`5.0`. The sanitizer lines are not optional: `sanitize_settings()` is a strict rebuild-from-scratch allowlist registered as the option's `sanitize_callback`, so a key it does not write is dropped on every save. Covered by `tests/AdminSpecificityFieldsTest.php` (render, saved-value render, accept, clamp high and low, default-when-missing, the zero case, the checkbox, and that every key is written).
- **A browser-config parity guard, so a key the bundle reads can no longer be settable from nowhere (`tests/BrowserConfigParityTest.php`).** Root cause of the `filterFieldDescriptions` bug below and of the missing specificity settings above: nothing asserted that the config this plugin emits covers what `assets/js/scolta.js` reads off it, so a browser-side read could exist with no corresponding localize entry and CI stayed green. The new test calls `Scolta_Shortcode::render()`, reads the captured `wp_localize_script()` array, and diffs its key set against keys parsed out of the committed bundle in both directions, recursing one level into `scoring` and `endpoints` so a missing sub-key cannot hide behind a passing top-level check. Forward allowlist is `priority_pages` alone (caller-supplied through the scolta-php `createInstance()` API); reverse allowlist is `container` (read only by `autoInit()` off the global) and `nonce` (emitted for the REST API, absent from `scolta.js`), each with its justification as a code comment. Three tripwire assertions on the extracted counts run before any diff, so a reformat of the bundle that breaks the extraction fails loudly instead of passing while asserting nothing. - **`get_api_key_source()` reported Amazee.ai while an explicit key served every request, because reporting and resolution were two derivations with opposite precedence (`includes/class-scolta-ai-service.php`, `admin/class-scolta-admin.php`, `includes/class-scolta-rest-api.php`, `cli/class-scolta-cli.php`, [#186](https://github.com/tag1consulting/scolta-wp/issues/186), parent [scolta-php#252](https://github.com/tag1consulting/scolta-php/issues/252)).** Root cause: `from_options()` gave an explicit key — `SCOLTA_API_KEY`, the wp-config.php constant, or the legacy database option — priority over stored Amazee credentials and returned before it ever looked at the credential store, while `get_api_key_source()`, which every admin and CLI surface called, checked `Scolta_Amazee_Config_Storage::load()` **first** and returned `'amazee'` before it had looked at the environment at all. Nothing forced the two to agree, and they did not: a site with a perfectly valid key sent every request with that key while the settings screen displayed "Connected to Amazee.ai (managed gateway)" in a success notice, the provider select preselected Amazee in the empty state, and the status table named the wrong provider. The class docblock documented the wrong order too, listing Amazee first — the order the *reporting* path applied, not the one the client used. Declaring a version in a package published from version control overrides the version Composer derives from the branch or tag, and that is what `branch-alias` exists to describe; `composer validate` has been reporting it as "The version field is present, it is recommended to leave it out if the package is published on Packagist" for as long as it has been there, but nothing in CI ran `composer validate`. This plugin is not the one that visibly broke — Packagist ignores a declared version, so `tag1/scolta-wp` resolves correctly — but the sibling Drupal adapter carried the identical antipattern and the drupal.org Composer facade honours the declared string, which broke a client build on 2026-07-27 (a site constrained to `dev-1.0.x` could `composer update` but never `composer install` from the resulting lock). The plugin header in `scolta.php` is the source of the version here, as it always was for WordPress; the `SCOLTA_VERSION` constant and `readme.txt` `Stable Tag` must still match it, so `scripts/validate-release.php` checks three locations instead of four. New `scripts/plugin-version.sh` reads the header, and the `dist-build`, `plugin-check` and release `check-readme-changelog` jobs that used to name the zip from `composer.json` now go through it. `version-sync` reads the header too. Both `validate-release.php` and a new `version-consistency` CI step fail if a `version` key reappears; pinned by `VersionConsistencyTest::test_composer_json_declares_no_version`.
- **The asset parity check verified nothing, and had not been able to fail since it was written.** `composer.json` ran `copy-assets` from `post-install-cmd` and `post-update-cmd`, and `copy-assets` overwrites the four committed browser assets from `vendor/tag1/scolta-php/assets/`. In CI the hook fired during `composer update`, **before** the "Verify duplicated assets match canonical" step ran, so that step compared a file Composer had written moments earlier against the manifest of the source it wrote it from. It printed cheerful `OK:` lines for every asset and could not go red on a stale committed copy, ever. Roughly 87 lines of shell verifying nothing. Two consequences, both real rather than theoretical: **(1)** the `test` job rewrites `composer.json` to require `tag1/scolta-php: dev-main@dev` from a VCS repository, so on a coordinated pull request the hook replaced the branch's new bundle with `main`'s old one and the suite then ran the old bundle, meaning a coordinated change had never been exercised by its own CI before merge; **(2)** it is the mechanism behind the stale `.sha256` sidecar recorded below, which drifted for two revisions precisely because `copy-assets` never touched it. The defect was not the step ordering. Any ordering fix would leave the pipeline one added `composer install` step away from reintroducing the hole, in any job, forever: a fixer and a checker in the same pipeline is the bug class, and the fixer always wins. Note who the hook actually served — Composer runs scripts only from the root package, so it never fired when a site installed the plugin. It ran in exactly two places: this repository's own CI, where it destroyed the check, and a developer's local checkout, where it silently mutated a tracked file.
- **`composer copy-assets` could not fail.** Every line read `[ -f vendor/… ] && cp … || true`, so when the vendored source was missing the script succeeded and copied nothing, leaving whatever stale bytes were already committed. A copy step that cannot fail is not a copy step. The guards are gone; the script now matches the Drupal adapter's and stops with a real error if a source is absent. Pinned by `StructuralIntegrityTest::test_copy_assets_fails_when_a_source_is_missing`.
- **`assets/js/scolta.js.sha256` had been stale since the facet-index re-vendor.** That re-vendor (#179) updated `assets/js/scolta.js` but not its sidecar, leaving the recorded hash describing a bundle two revisions old. Nothing in CI reads the sidecar today — the asset-parity job checks the committed bundle against scolta-php's `assets/ASSETS.sha256` manifest — so it went unnoticed, but the file is documented as tracking the bundle and every prior re-vendor refreshed it. Refreshed here alongside the bundle it describes.
- **Filter field descriptions never reached the browser, so the labelling feature was dead client-side (`includes/class-scolta-shortcode.php`).** `scolta.js` reads `instanceConfig.filterFieldDescriptions` to label filter groups in the sidebar, and this plugin had the entire rest of the feature already: an admin field, a render callback, a sanitizer, and a REST layer that passes the map into the AI expansion prompt server-side. The `wp_localize_script()` array simply omitted the key, so the browser fell back to `{}` and no configured description ever appeared. Root cause is not the omission itself but that nothing could catch it: no test in any Scolta package asserted that the emitted browser config covered what the browser reads, so a missing bridge looked exactly like a working one with no descriptions configured. Fixed by emitting `'filterFieldDescriptions' => $config->filterFieldDescriptions`, and permanently guarded by the new `tests/BrowserConfigParityTest.php`. Covered by `tests/ShortcodeTest.php` (key present in the localized array, and a non-empty configured map round-trips).
- **Re-vendored `assets/js/scolta.js` and the bundled scolta-core WASM from scolta-php.** Picks up the identifier/proper-noun search fix: expand_query rule 16 (NAMED ENTITY / EVENT → DEFINING DETAILS), summarize/follow_up grounding rules that forbid claiming the collection lacks content the model cannot see, and the new `[No result matched the full query; ...]` context marker that tells the summarizer when it is looking at an OR-fallback result set.

### Known limitations
- **Facet counts do not exactly match the filtered result list once AI query expansion has run ([tag1consulting/scolta-php#265](https://github.com/tag1consulting/scolta-php/issues/265)).** The panel recounts after expansion, which it did not do before this release, and on every corpus measured it is strictly closer to the list than the previous behaviour was. ## [0.3.2] - 2026-04-24

Coordinated release. Fixes memory and CLI visibility regressions surfaced by a 44,107-page real-world WordPress deployment.

### Fixed
- **Silent CLI during 52-minute build**: `do_build_php()` was passing neither a `LoggerInterface` nor a `ProgressReporterInterface` to `IndexBuildOrchestrator::build()`, so all progress output went to `NullLogger`/`NullProgressReporter`. Added `Scolta_WP_CLI_Logger` (PSR-3 bridge to `WP_CLI::log`/`::warning`/`::debug`) and `Scolta_WP_CLI_Progress_Reporter` (wraps `WP_CLI\Utils\make_progress_bar`); both are now passed to `build()`. (#6)
- **Peak RAM on large corpora (observed 2,870 MB on 44k-page site)**: `Scolta_Content_Gatherer::gather()` used `WP_Query( 'posts_per_page' => -1 )` and returned a materialized `ContentItem[]` array, pre-loading every post into memory before the streaming indexer ran. Now returns a `\Generator` that paginates `WP_Query` in batches of 100 and calls `wp_cache_flush_group('posts')` between batches. Posts now flow through the pipeline one batch at a time. The gather-upstream eager-load was always present; 0.3.1 appeared to fix OOM because the streaming finalize removed the finalize-time doubling, but gather-side was unfixed until now. (#6)

### Added
- **Flexible memory budget and chunk size**: The Memory Budget admin field now accepts profile names (`conservative`, `balanced`, `aggressive`) **or** a raw byte value (`256M`, `1G`) in addition to the three preset profiles. A new **Chunk Size** admin field lets you set pages-per-chunk independently of the memory budget — leave it blank to use the profile default (50/200/500). Both values can also be overridden per-run via `--memory-budget=<budget>` and `--chunk-size=<n>` on `wp scolta build` and `wp scolta diagnose`. (#8)
- **`wp scolta diagnose`**: New WP-CLI command that profiles the PHP indexer pipeline in three isolated phases — gather (WP_Query + `apply_filters('the_content')` + `get_permalink`), HtmlCleaner, and indexer — on a configurable post sample (default 500). Prints per-phase ms/post, projects the full-corpus duration, and emits a recommendation identifying the dominant bottleneck. Use this to determine whether a slow build is caused by WordPress content filters, HTML cleaning, or the indexer itself. (#8)
- **`Scolta_Content_Gatherer::gatherCount(): int`**: COUNT-only query using `WP_Query` with `fields='ids'`, returning just the integer count. Used by `do_build_php()` for the early-exit check and to pre-size `BuildIntent` without loading post content. (#6)
